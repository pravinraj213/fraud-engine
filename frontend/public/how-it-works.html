01 / THE BIG PICTURE

One transaction. Four steps.

The API evaluates a transaction against the account’s earlier activity, saves the result, and makes the evidence available to a reviewer.

  1. 01

    Receive

    A client or simulator submits the account, amount, merchant, location, and time through POST /api/transactions.

  2. 02

    Evaluate

    Enabled rules inspect account history before the new transaction is inserted. Each triggered rule returns a score and a reason.

  3. 03

    Save & alert

    The transaction, assessment, and rule hits are stored together in SQLite. A HIGH result schedules an alert in the background.

  4. 04

    Investigate

    Flagged transactions enter the review queue. A reviewer examines the evidence, records a decision, and can add a note.

02 / DETECTION RULES

Understand the reason behind the flag.

These are the default settings. Weights, thresholds, and enabled rules can be configured; the console’s Rules page shows the running configuration.

01 / FREQUENCY

Transaction velocity

More than five transactions on one account within ten minutes, including the current transaction.

40 points for the sixth transaction.
Each additional transaction adds 15, up to 100.
02 / SPENDING

Unusual amount

Compares spending with up to 50 prior amounts. Triggers at a z-score of 3 or at five times the median. A z-score measures how far spending is above the account’s average.

50 points, or 80 at z ≥ 6 or ≥ 10× median. With fewer than five prior transactions, INR 100,000 or more scores 50.
03 / LOCATION

Impossible travel

Checks whether travel from the previous transaction’s location would require a speed above 900 km/h. Distances below 100 km are ignored.

70 points, or 90 above 1,800 km/h. Qualifying locations at the same moment also score 90.
03 / RISK SCORING

Several signals. One priority.

The engine multiplies each triggered rule’s score by its weight, adds the results, rounds the total, and caps it at 100. Default weights are all 1.0.

Total score = min(100, round(Σ triggered rule score × weight))
NONENo hitsCLEAN · outside the queue
LOWBelow 40With a rule hit · FLAGGED
MEDIUM40–69FLAGGED · needs review
HIGH70–100FLAGGED · alert scheduled

A worked example

The sixth transaction in ten minutes also triggers the standard unusual-amount rule. Two signals combine into a HIGH assessment.

Velocity40 × 1.0
Unusual amount50 × 1.0
Total risk score90 / 100 · HIGH

A score is a rule-based priority, not a probability of fraud. A score of 90 does not mean a 90% likelihood of fraud.

04 / ALERTS & HUMAN REVIEW

Evidence first. A recorded decision next.

How alerts are delivered

  • Only HIGH assessments schedule an alert. In log mode, it is written to the server log. In SES mode, it is emailed to configured recipients.
  • The email contains transaction details, a risk score, rule explanations, and a link to the reviewer console.
  • A unique notification record is claimed before sending to prevent duplicate attempts for the same assessment.
  • The default cap is 20 sent alerts per rolling 24 hours. Failed sends and attempts beyond the cap are recorded as FAILED.

Console links must be reachable from the recipient’s device. Localhost addresses are shown as text with instructions.

How reviewers resolve a flag

Enter your reviewer name, open a transaction, inspect its rule evidence, and choose the appropriate decision.

FLAGGED→REVIEWED→CLEARED
  • Reviewed: confirmed or escalated as suspicious.
  • Cleared: assessed as legitimate or a false positive. A flagged transaction can also be cleared directly.
  • Clearing is final. A reviewed transaction can later be cleared.
  • Each action stores the reviewer name, timestamp, and optional note in the review history.
05 / TRY THE WORKFLOW

See a decision take shape.

  1. Open the Simulator and check the alert mode. Log mode is the default. To enable email, open Email alerts off in the console header, verify the displayed recipient, and select Turn on email alerts.
  2. Select scenarios and run them. Compare expected results with the engine’s actual decisions.
  3. Open a flagged result to inspect its transaction details and rule evidence.
  4. Enter a reviewer name, add a note, and mark the transaction reviewed or cleared.
  5. Return to the review queue and use status, risk, and account filters to find it again.

The email toggle applies to new transactions for the current server session. Restarting restores the startup setting. Simulator traffic is saved to the same database as other transactions. In email mode, the simulator asks you to acknowledge that it can send real alerts.

FURTHER DETAILS

Under the hood

What runs the system?

A React console calls a FastAPI backend. Services manage ingestion and reviews; repositories store transactions, assessments, rule hits, review actions, and notifications in SQLite. Rules read history without writing to the database. Amazon SES delivers email when enabled.

Can I add or tune a rule?

Yes. Configure rule weights and parameters in backend/rules.yaml and the high-risk threshold through HIGH_RISK_THRESHOLD. Restart the backend to load changes. New rules implement the rule interface and register through the existing plugin mechanism. See docs/ADDING_A_RULE.md for a worked example.

What are the current limitations?

Reviewer names are typed in; authentication is not implemented. Background alerts have no durable outbox or automatic retry, so a server interruption can lose an alert. The app uses SQLite and supports INR transactions. This version flags activity for investigation; it does not block payments.

How are money and time handled?

The API accepts and returns money as decimal strings, such as "4999.00". Timestamps use UTC. Alert emails display the transaction time in UTC; the console formats dates for the reviewer’s locale.
